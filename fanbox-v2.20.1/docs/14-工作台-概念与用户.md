## 0. 一句话

**FanBox 解决「此刻 agent 在我机器上干了什么」；工作台解决「这些项目在时间里往哪走」。**

- 驾驶舱：实时、单会话、看与接管。
- 账本：长期、跨会话、决定与交接。

这不是给 FanBox 加三个功能块，而是补两层：

- **意图层**：为什么做、不做什么、否决过什么。
- **时间层**：做过什么、留下什么、下一步是什么。

知识图谱是意图的关系网，待办是意图的队列，任务档案是时间的证据链。三者不是三个模块，而是同一本账的三个切面。

## 1. 问题不是「记不住」，是「接不上」

### 1.1 意图断裂

方案设计发生在脑子里、聊天里、临时文档里。agent 执行时只看得到当前 prompt。

后果：三周后它再次提议你早就否决过的方案；你只记得「当时好像说过不行」，说不出为什么。

### 1.2 时间断裂

FanBox 的项目记忆是会话流水：哪天聊了什么、改了哪些文件。它不是项目状态。

后果：离开一周回来，要翻终端、翻 diff、翻聊天，花半天考古「做到哪、为什么停」。

### 1.3 注意力断裂

agent 停下来等你确认时，你不在电脑前。手机现在能收到通知，但不能做决定。

后果：一次等待变成一天停滞；或者你在手机上回了一句模糊的话，agent 按错误理解继续跑。

三个断裂指向同一件事：**缺一份人能和 agent 共读的项目账本。**

## 2. 为什么在 FanBox 上做，而不是再开一个 Notion

因为难的不是「写文档」，是「文档和执行接在一起」。

| 能力 | 通用笔记 / 项目管理工具 | FanBox 已有 |
|---|---|---|
| 文档读写 | ✅ | ✅ 文件树、预览、Markdown 编辑 |
| 知道 agent 干了什么 | ❌ | ✅ 终端、hooks、diff、会话记忆 |
| 把任务交给 agent | ❌ | ✅ 内嵌终端、Agent 控制接口 |
| 验收产出物 | 弱 | ✅ 本回合 diff、HTML/Markdown 预览 |
| 人不在电脑前 | 靠云 | ✅ 微信遥控、离开时叫我、断线续跑 |
| 长期常驻 | 靠云 | ✅ 合盖继续、值守、自动续跑 |

另起一个笔记应用，等于把右半张表全部重造一遍，还接不上执行。反过来，FanBox 没有账本，就永远只是一个「当下很好用、过一周就失忆」的驾驶舱。

**定位**：不是笔记应用，不是项目管理工具，是**附着在工作现场的项目账本**。

## 3. 核心抽象

### 3.1 项目账本

每个项目一个目录，加一份账本。账本只有三类东西：

- **知识**：需求、缺陷、决策、创意、资料、产物。
- **待办**：从知识里长出来的可执行项。
- **任务档案**：一次下发给 agent 的完整生命周期。

账本跟着项目走，放在 `.workbench/`，可以进 git，可以离线，可以整体搬走。

### 3.2 知识不是文档集合，是关系

文档只是节点。真正值钱的是边：

- 这个需求由哪个决策实现？
- 这个缺陷是哪个改动引入的？
- 这个方案推翻了哪个旧方案？
- 这个产物是哪次任务产生的？

**图谱的价值不是好看，是让 agent 接任务时自动带上相关决策与否决理由，让你半年后还能看懂「为什么是这样」。**

节点与边的设计见 PRD §3。这里只立三条原则：

1. 文档是唯一事实源，图是投影，不手工维护第二份数据。
2. 关系用固定小词表，不允许自由发挥。
3. 每个视图只回答一个问题，不做「什么都想看」的宇宙图。

### 3.3 待办是意图的队列

待办不是许愿池，它要能被清空。来源只有四种：

- 需求：要做的新东西。
- 缺陷：坏了要修。
- 创意：先记下来，未必做。
- 维护：升级、清理、补文档。

每条待办必须有「下一步动作」或「明确的等待条件」，否则它只是创意，应该留在收件箱。

### 3.4 任务是把意图翻译成执行的单元

任务是契约，不是聊天。一份任务至少有五件东西：

1. **目标**：做完是什么样。
2. **上下文**：必读的文档、相关决策、已否决方案。
3. **约束**：不能碰什么、不能怎么做。
4. **证据**：产物、diff、测试结果、验收记录。
5. **结论**：做完之后的复盘与知识回写。

**任务不等于会话。** 一个任务可以有多轮尝试（attempt）：第一次跑偏、打回重做、断线续跑，都记在同一份档案里。会话是执行现场，任务是账本条目。断线续跑不新开 attempt；只有打回或显式重开才 +1。

**不是每个任务都要完整契约。** 当天的小活走 `quick`：单文件或小范围、不碰依赖/配置/迁移、一句话目标与完成标准、一行记录；越界自动升级 `full`。跨天、跨会话、要审计的走 `full`，五件齐全。

### 3.5 过程不是聊天记录，是时间线

过程登记分三层：

- **事件层**：hooks、改动文件、diff 统计、session id，落 `events.jsonl`，全量、不进 git，供审计与问题定位。它是现有 `termFacts`/hooks 的任务域投影，不造第二套事实。
- **时间线层**：里程碑、决策、卡点，落 `log.md`；你的批注落 `notes.md`。两者都进 git。
- **关单层**：目标、做法、结果、坑、后续，落 `summary.md`，永久保留，进 git。

界面默认只展示后两层，事件层收在「原始事件」里。只记事件会变成噪音，只记时间线会漏证据。

## 4. 用户

### 4.1 现在的你：设计者 / 维护者

- **状态**：多项目并行，方案在脑子里，手上同时在指挥几个 agent。
- **诉求**：记录不能打断设计；下发不超过三步；验收要一眼看到证据。
- **反诉求**：不想维护一套复杂的项目管理数据；不想为图谱填表。

### 4.2 一周后的你：回归者

- **状态**：刚回来，记忆已经掉了大半。
- **诉求**：10 分钟内知道每个项目「做到哪、为什么、下一步、哪里有坑」。
- **反诉求**：不想读完整聊天记录；不想看 200 条自动日志。

### 4.3 agent：第一读者

- **状态**：每次接任务都从零开始，只会读你给它的文件。
- **诉求**：机器可读的上下文、明确验收、稳定 ID、小文件、清晰的权限边界。
- **反诉求**：模糊的「你懂的」、散落在聊天里的约束、需要猜的目录结构。
- **权限**：任务过程、log、产物可直接写；需求、缺陷、决策只能提交提议，由人确认落库。

**如果账本不能直接被 agent 读，它就只是日记，不是控制面。**

### 4.4 未来的协作者：本期不服务

- 文档保持人类可读，交接时能看懂。
- 但第一版不做多人、权限、实时协作、评论。为一个人做到极好。

## 5. 设计原则

1. **文件即真相**：无数据库、可 git、可离线、可迁移。索引可删可重建。
2. **记录自动，判断留人**：过程由 hooks 和 diff 自动登记；只有「要不要做、算不算完成、要不要推翻」由你点。
3. **图谱是投影**：从文档链接推导，禁止为了图而填表；图答不出问题就不画。
4. **任务有契约**：没有目标和验收的任务不许下发；agent 只能提议完成，验收权默认在人。人可以在建任务时显式标为低风险并预设机器门槛，只有门槛全过才允许自动通过，且保留 24 小时撤销权。
5. **手机是遥控器**：30 秒内完成看、批、发；不做缩小版桌面。
6. **先服务一个人**：不为假想的团队牺牲你的顺手。
7. **克制**：不做通用笔记、不做项目管理、不做云、不做账号。

## 6. 与 FanBox 的边界

| FanBox 已有 | 工作台怎么用 | 不改什么 |
|---|---|---|
| 文件树 / 预览 / 编辑器 | 账本的读写界面 | 不改成笔记应用 |
| 内嵌终端 + hooks | 任务执行现场与过程登记 | 不做 headless 黑箱 |
| 本回合 diff | 验收证据 | 不替代 git |
| 指挥台 / 离开时叫我 | 任务等待与手机通知 | 不扩大打扰 |
| 微信遥控 / 值守 | 手机批准、回答、下发 | 不做全功能移动端 |
| 断线续跑 / 合盖继续 | 长任务可靠性 | 不改电源策略 |
| Agent 控制接口 | 任务下发与等待 | 不开放持久 token |

**补齐的只有两样**：账本的数据形态，以及账本在界面上的位置。

## 7. 三个叙事

### 7.1 一个方案诞生的下午

你写下 ADR-003「导出走本地 canvas，不引第三方渲染库」，顺手关联 REQ-009。

从 REQ-009 拆出 T-012，点「下发」：新建一个项目目录下的终端 tab，agent 先读 brief，再动手。

它每过一个里程碑往 log.md 加一行，产物登记到 artifacts.md，diff 自动进证据。

傍晚它说「做完了」，任务进入待验收；你在手机上看到摘要和两张对比图，回一句「批准」。

结论回写：REQ-009 标完成，ADR-003 标已实现，留下一条「4K 屏空白条」的坑。

### 7.2 离开一周

回来打开工作台，第一屏不是 200 条日志，而是一张回归摘要：

- 3 个项目有进展，2 个任务完成，1 个卡在等你决策。
- 1 个缺陷超期 9 天。
- 建议下一步：先批 T-018，再处理 DEF-011。

点进去才看细节。10 分钟恢复上下文。

### 7.3 半年后

agent 提议「用 Redis 做缓存」。你打开 ADR-007，看到当时的否决理由、成本测算，以及后来 T-044 的实测结论。图谱上这条决策连着两个被它推翻的旧方案。

你不用重新想一遍，agent 也不用重新猜一遍。

## 8. 怎么算成了

**一句话**：离开一周回来，10 分钟内能看清每个项目「做到哪、为什么、下一步」，并把下一个任务交给 agent 继续跑。

六个信号：

1. 新项目 30 秒建好账本，不需要读文档。
2. 一个灵感 3 秒进收件箱，不需要先想归类。
3. 一个任务 30 秒下发，brief 自动带上下文。
4. 每次验收都有证据，不靠回忆。
5. 一周回归 10 分钟，不靠考古。
6. agent 接任务不用你重复解释上周说过什么。

## 9. 已定与待共创

已定（2026-11-15）：

- **命名**：案台（FanBox Workbench）。
- **形态**：FanBox 内新增「案台」视角，不另起应用。
- **规模**：日常 3-5 个活跃软件项目；工程上限 20 个项目。
- **账本**：项目内 `.workbench` Markdown，图谱从链接推导；新项目默认建，旧项目手动加入、只导关键文档。
- **执行**：一任务一终端 tab，复用 hooks 与 diff。
- **手机**：微信为主，飞书只发；首批批准/打回 + 回答等待，第二批追问 + 快速捕获。
- **图谱第一版**：追溯列表 + 局部邻域，不做装饰性全局地图。
- **知识写入**：agent 提议制，人确认落库；任务过程与产物可直接写。
- **验收**：默认人验收；低风险任务可按预设门槛自动通过，默认全局关、按项目开启，保留 24 小时撤销权。
- **过程**：三层记录——`events.jsonl` 全量不进 git，`log.md` 写里程碑，`summary.md` 关单；界面默认只展示后两层。
- **任务档位**：`quick` / `full` 两档；quick 限单文件/小范围、不碰依赖/配置/迁移，越界自动升级 full。
- **冻结范围**：六类模板、状态枚举、任务 `links`、验收表；`_ids.json` 记录 ID 高水位。
- **运行模式**：`wb` 在线走 IPC，离线走原子写 + `.wb.lock`；approve 只认人。
- **S0**：不实现自动通过；先用 `wb task verify` 在可见终端跑手工验收。
- **attempt**：只有打回/显式重开 +1；续跑与恢复不 +1。

待验证：

1. **低风险门槛**：哪些任务算低风险、默认阈值定多少（见 PRD §3.8）。
2. **平台**：Windows 桌面壳是否可用，决定 S1 的终端下发能否验收。
